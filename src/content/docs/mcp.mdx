## Endpoint

The canonical hosted MCP resource is:

```text
https://mcp.qyl.at/mcp
```

The root `https://mcp.qyl.at/` is a product page, not a second protocol endpoint. `/healthz` is the platform health check.

## Add it from a client

For Claude Code:

```bash
claude mcp add --transport http qyl https://mcp.qyl.at/mcp
```

A compatible client discovers the protected-resource metadata, identifies itself through a client metadata document (CIMD) or dynamic registration (DCR), and opens Authorization Code with PKCE for the exact resource `https://mcp.qyl.at/mcp`. Hosted access requires `qyl:read` and an explicit Auth0 client grant; registering a client alone does not grant access. The [write tools](#write-tools) also need `qyl:write` (create and update) or `qyl:delete` (delete).

For ChatGPT, add the same endpoint as an OAuth MCP connection and include `qyl:read` in its base scopes, plus `qyl:write` and `qyl:delete` for the write tools. Complete the qyl service login and consent. This is a custom connection; public directory submission is still in preparation.

## Authentication boundary

qyl acts only as an OAuth 2.1 Resource Server. Auth0 at `https://qyl-eu.eu.auth0.com/` owns authorization and token issuance. The qyl server verifies:

- the exact issuer;
- the exact resource audience;
- the `qyl:read` scope on every request, and `qyl:write` or `qyl:delete` for a write tool;
- expiry and the RFC 9068 access-token profile;
- the token signature through the issuer’s JWKS.

There is no proprietary static bearer-token path and no embedded anonymous authorization server.

## Write tools

The read tools stay read-only. Five separate tools change something, so a client can approve reads and writes separately. They change only annotations and saved queries in the qyl project your account is authorized for:

| Tool | Changes | Scope |
| --- | --- | --- |
| `create_annotation` | adds a plain-text note of at most 2000 characters on a trace, span or session | `qyl:write` |
| `update_annotation` | replaces a note's text; what it is attached to stays fixed | `qyl:write` |
| `create_saved_query` | adds a named filter for traces, logs or metrics | `qyl:write` |
| `update_saved_query` | renames it or replaces its description or filter | `qyl:write` |
| `delete` | removes one annotation or saved query (`kind` is `annotation` or `saved_query`) | `qyl:delete` |

`list_saved_queries` and `run_saved_query` read saved queries with `qyl:read`, and `get_trace` and `list_sessions` return the annotations on what they read. No tool deletes or edits traces, logs or metrics, deploys or rolls back software; retention removes telemetry.

Updates and deletes take the object's `etag` and send it as `If-Match`: a stale etag fails with `precondition_failed` instead of overwriting a newer version, and a duplicate saved-query name fails with `conflict`. A call whose token lacks the scope it needs gets `403` with `WWW-Authenticate: Bearer error="insufficient_scope"` naming the scopes to request, before the tool runs, so the client can re-authorize. A transport without that challenge returns the refusal as a tool error with the code `insufficient_scope`, for example “Reconnect qyl and allow qyl:write to use it.”

## Local alternative

For a same-machine client, run the published server over stdio:

```bash
npx -y qyl-mcp-server --stdio
```

The stdio server exposes the same tools, the write tools included, and MCP Apps without creating an Internet-facing listener. Without OAuth there is no scope to check: the `write` and `delete` roles of the Collector key you configure decide whether a write succeeds, and demo mode (`QYL_DEMO=1`) refuses the annotation and saved-query tools.

Both transports use SDK v2 to serve `2026-07-28` and supported 2025-era tool clients. The workbench explicitly enables `versionNegotiation: { mode: "auto" }`; the SDK Client's own default remains the 2025 handshake. See [protocol support](/docs/protocol-2026-07-28/).

## Optional ChatGPT Events

On a supported ChatGPT connection using `2026-07-28`, `trace.error` subscriptions can report matching errors, optionally filtered by service. Enabling the feature does not subscribe anyone automatically. Ordinary read tools remain available to clients without Events support.

An operator enables Events by configuring `MCP_EVENTS_STORE` on an authenticated deployment with persistent storage and the access checker described in the [server configuration](https://github.com/ANcpLua/qyl.mcp#mcp-events). The store retains subscription owner/client identifiers, callback and filter settings, signing keys, and expiry. It does not retain subscribers' OAuth access or refresh tokens or copy the collector's telemetry. Expiration, revoked access, or unsubscribe removes the subscription and stops delivery.
