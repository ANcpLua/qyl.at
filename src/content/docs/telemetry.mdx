## Three owned boundaries

qyl keeps protocol ownership explicit:

1. OpenTelemetry owns OTLP ingestion and the telemetry vocabulary.
2. `qyl-api-schema` owns every Qyl read request, response, stream event, and error.
3. The MCP SDK owns JSON-RPC, transport, tool-result, and resource-result envelopes.

The collector maps internal DuckDB rows into generated Qyl contracts before data crosses an HTTP, streaming, MCP, or generated-client boundary.

## One registry, generated everything

The telemetry vocabulary has a single source: one Weaver registry that resolves the upstream OpenTelemetry semantic conventions, the gen-ai conventions, and qyl's own attributes as YAML in the same registry. There is no second vocabulary and no merge step after Weaver.

The C# constants are emitted from that registry by Weaver templates and committed to the repository, so what the compiler sees is diffable and CI fails on a stale regeneration rather than on a mismatch at runtime.

Three rules follow, and each has exactly one owner:

- **The instrumentation never normalizes.** It writes only constants the generator produced. A vendor key travels as a tag; the application does not rename it. That is also what makes the collector viable under Native AOT, where a runtime rewrite table has nowhere to live.
- **The collector renames and drops** according to the `AttributeMapping` generated from the same registry, and counts every drop on `qyl.collector.attributes.dropped`. A missing attribute is a number you can query, not silence.
- **Nothing invents keys.** The mapping may only point at attributes the registry defines, and Weaver's live-check judges the telemetry qyl actually emits against the registry's own `.weaver.toml` and advice policies.

New term, new span, new vendor: registry YAML, instrumentation, mapping table. One place each.

## Ingestion

The collector accepts official OTLP protobuf or JSON for traces, logs and metrics, and retains all three in DuckDB. Profiles are not supported.

In production, the OTLP receiver requires `x-otlp-api-key`. Local development defaults to unsecured loopback listeners.

## MCP operation telemetry

qyl.mcp records client and server operation spans and duration histograms using the pinned OpenTelemetry MCP semantic vocabulary. Standard W3C trace context and baggage travel in MCP `params._meta`; inbound server spans use valid remote context as their parent.

The workbench does not record prompt variables, tool arguments, tool results, or
arbitrary HTTP headers as span attributes. Operation logs and the live protocol
journal are metadata-only unless content capture is enabled explicitly. The
collector persists only a small positive allowlist of known-safe HTTP header
attributes and always rejects credentials, cookies, and `Mcp-Param-*`.

## Explicit demo mode

Live collector errors remain errors. To run the fixture-backed demonstration deliberately:

```bash
QYL_DEMO=1 bun run start:workbench
```

Every generated tool result carries `mode: "demo"`, so the presentation can label it rather than presenting a fixture as collector evidence.
