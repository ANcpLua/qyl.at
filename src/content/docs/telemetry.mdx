## Ownership and compatibility

OpenTelemetry defines the SDK APIs, exporters and OTLP wire format. qyl keeps the official .NET and JavaScript SDKs and exporters where it uses them, and receives standard OTLP from other languages. qyl owns its instrumentation, registry extensions, generated bindings and collector capture policy.

These responsibilities have separate sources:

| Boundary | Source and owner |
| --- | --- |
| Telemetry attributes and metrics used by qyl | The qyl Weaver registry, resolved from upstream language-independent semantic conventions, verified vendor definitions and qyl extensions |
| C# and TypeScript telemetry bindings | Generated from that registry in the SemanticConventions repository |
| Product API requests, responses, stream events and errors | The independent `qyl-api-schema` contract, generated for .NET and TypeScript |
| OTLP messages | Official OpenTelemetry protobuf definitions |
| MCP JSON-RPC and result envelopes | The official MCP SDK |

Telemetry bindings name attributes, enum values, events and metrics. The product API contract describes the data qyl returns to clients. Updating one does not automatically change the other.

## One registry, two languages

qyl generates C# and TypeScript semantic-convention bindings from the same resolved registry. The three `Qyl.Telemetry.SemanticConventions` NuGet packages and `@ancplua/qyl-semantic-conventions` share version {versionOf("Qyl.Telemetry.SemanticConventions")}. The C# packages separate stable and incubating conventions and provide an analyzer; the TypeScript package exposes its stable bindings at the package root and its incubating bindings at `@ancplua/qyl-semantic-conventions/incubating`. Generated outputs are committed and checked for drift, so a vocabulary change is reviewable alongside its registry input.

qyl-owned .NET instrumentation and MCP operation telemetry use these generated names with the official SDKs. The qyl CLI runner already activates `Qyl.Telemetry.Hosting` through `AddQyl()` for its own diagnostics, exporting only when its dedicated diagnostics endpoint is configured. The collector and API hosts use the same producer pipeline. Generated constants do not update third-party instrumentation: another library can still emit an older attribute name. A newer SDK or an OTLP `schema_url` does not, by itself, rewrite those attributes.

## What the collector changes

The collector normalizes known attribute names before capture policy decides what to retain:

- Generated rename rules translate recognized deprecated keys into canonical keys. The collector also handles four legacy aliases: `gen_ai.system`, `gen_ai.usage.prompt_tokens`, `gen_ai.usage.completion_tokens` and `agents.tool.call_id`.
- When both spellings are present, the value explicitly supplied under the canonical key wins, regardless of input order.
- Verified vendor attributes keep their vendor spelling where pass-through is allowed. Privacy denials still apply; vendor pass-through is not permission to retain credentials or personal data.
- Signal-specific capture policy can drop disallowed or unrecognized attributes. Dropped attributes are counted in `qyl.collector.attributes.dropped`.

For example, a recognized `http.method` attribute becomes `http.request.method`. This is a known-key conversion, not a promise to translate any incoming schema. The incoming `schema_url` is metadata; it does not select or execute an arbitrary schema transformation.

The collector must understand new vocabulary before qyl-owned emitters adopt it. Compatibility checks cover older and current keys, canonical-key precedence, vendor pass-through and capture denials. See the [SemanticConventions source](https://github.com/ANcpLua/Qyl.Telemetry.SemanticConventions) and the [collector ingestion source](https://github.com/ANcpLua/qyl/tree/main/services/qyl.collector.ingestion).

## Ingestion

The collector accepts official OTLP protobuf or JSON for traces, logs and metrics, and retains all three in DuckDB. Profiles are not supported.

In production, the OTLP receiver requires an `x-otlp-api-key` credential with the explicit `ingest` role. Configure each `QYL_OTLP_PROJECT_KEYS` entry as an object with `key` and a nonempty `roles` array; string-only keys and missing roles fail startup. Roles are independent: ingest access grants no product API permissions, and `read`, `write` or `delete` access grants no ingest permission. Local development defaults to unsecured loopback listeners.

## MCP operation telemetry

qyl.mcp records client and server operation spans and duration histograms using the generated qyl registry bindings for the MCP semantic vocabulary. Standard W3C trace context and baggage travel in MCP `params._meta`; inbound server spans use valid remote context as their parent.

The workbench does not record prompt variables, tool arguments, tool results, or
arbitrary HTTP headers as span attributes. Operation logs and the live protocol
journal are metadata-only unless content capture is enabled explicitly. The
collector persists only a small positive allowlist of known-safe HTTP header
attributes and always rejects credentials, cookies, and `Mcp-Param-*`.

## Explicit demo mode

Live collector errors remain errors. To run the fixture-backed demonstration deliberately:

```bash
QYL_DEMO=1 bun run start:workbench
```

Every generated tool result carries `mode: "demo"`, so the presentation can label it rather than presenting a fixture as collector evidence.
