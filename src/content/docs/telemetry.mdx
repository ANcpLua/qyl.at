## Ownership and compatibility

OpenTelemetry defines the SDK APIs, exporters and OTLP wire format. qyl keeps the official .NET and JavaScript SDKs and exporters where it uses them, and receives standard OTLP from other languages. qyl owns its instrumentation, registry extensions, generated bindings and collector capture policy.

These responsibilities have separate sources:

| Boundary | Source and owner |
| --- | --- |
| Telemetry attributes and metrics used by qyl | The qyl Weaver registry, resolved from upstream language-independent semantic conventions, verified vendor definitions and qyl extensions |
| C# and TypeScript telemetry bindings | Generated from that registry in the SemanticConventions repository |
| Product API requests, responses, stream events and errors | The qyl API contract, written in TypeSpec in the qyl repository and generated for the Collector (C#) and the MCP server (TypeScript) |
| OTLP messages | Official OpenTelemetry protobuf definitions |
| MCP JSON-RPC and result envelopes | The official MCP SDK |

Telemetry bindings name attributes, enum values, events and metrics. The product API contract describes the data qyl returns to clients. Updating one does not automatically change the other.

## One registry, two languages

qyl generates C# and TypeScript semantic-convention bindings from the same resolved registry. The three `Qyl.Telemetry.SemanticConventions` NuGet packages and `@ancplua/qyl-semantic-conventions` share version {versionOf("Qyl.Telemetry.SemanticConventions")}. The C# packages separate stable and incubating conventions and provide an analyzer; the TypeScript package exposes its stable bindings at the package root and its incubating bindings at `@ancplua/qyl-semantic-conventions/incubating`. Generated outputs are committed and checked for drift, so a vocabulary change is reviewable alongside its registry input.

qyl-owned .NET instrumentation, MCP operation telemetry and the qyl.at browser Web Vitals emitter use these generated names with the official SDKs. The qyl CLI runner already activates `Qyl.Telemetry.Hosting` through `AddQyl()` for its own diagnostics, exporting only when its dedicated diagnostics endpoint is configured. The collector and API hosts use the same producer pipeline. Generated constants do not update third-party instrumentation: another library can still emit an older attribute name. A newer SDK or an OTLP `schema_url` does not, by itself, rewrite those attributes.

## Instrumenting a .NET application

`Qyl.Telemetry.Hosting` {versionOf("Qyl.Telemetry.Hosting")} configures instrumentation and export through
`builder.AddQyl()`. Its packaged `SKILL.md` contains the complete consumer guide.

- HTTP server/client calls, Npgsql commands and Kafka operations are instrumented automatically. AI chat and tool
  spans require `UseOpenTelemetry()` on the AI client. Build and host metadata supply `service.name`, `service.version`
  and `deployment.environment.name`.
- For application spans, create an `ActivitySource` and register its name with
  `options.AdditionalSources.Add(sourceName)`. The generated `Qyl.Spans` and `Qyl.IncubatingSpans` starters are optional
  alternatives for operations described by the registry.
- Use native `span?.SetTag("order.id", orderId)` attributes. Application-owned names and native values, including
  booleans, integers and arrays, retain their types. No prefix is added or required. Explicit Collector persistence
  and privacy rules still apply.
- Generated starters support `span?.RecordFailure(exception)`, which records error status and an exception event.
  A failure without an exception can use `RecordFailure(ErrorType.Custom("rate_limited"), "The provider answered 429")`.

Propagate the producer's `ActivityContext` when processing a message. Register custom AI source names with the tracer
provider, and choose the business attributes that identify the application's work. Those decisions belong to the
application; the compiler cannot infer them.

Exporter transport is explicit. `options.CollectorProtocol` defaults to HTTP/protobuf; set
`OpenTelemetry.Exporter.OtlpExportProtocol.Grpc` when the configured endpoint serves gRPC. A port number does not select
the protocol.

## Browser Web Vitals

qyl.at sends the generated `browser.web_vital` event through the official OpenTelemetry JavaScript log SDK and exporter. Each event carries the Web Vitals library’s real metric-instance ID, value, delta, rating and navigation type, with a bounded pathname and browser language. LCP and INP values and deltas are milliseconds; CLS is unitless. The instrumentation scope identifies the qyl schema. Cached pages using the older payload remain accepted through a legacy event path without inventing missing IDs or deltas. Viewport dimensions and device memory are not forwarded.

## What the collector changes

The collector normalizes known attribute names before capture policy decides what to retain:

- Generated rename rules translate recognized deprecated keys into canonical keys. The collector also handles four legacy aliases: `gen_ai.system`, `gen_ai.usage.prompt_tokens`, `gen_ai.usage.completion_tokens` and `agents.tool.call_id`.
- When both spellings are present, the value explicitly supplied under the canonical key wins, regardless of input order.
- Verified vendor attributes keep their vendor spelling where pass-through is allowed. Privacy denials still apply; vendor pass-through is not permission to retain credentials or personal data.
- Custom attributes do not need registry membership. Explicit persistence and privacy denials still apply; dropped attributes are counted in `qyl.collector.attributes.dropped`.

For example, a recognized `http.method` attribute becomes `http.request.method`. This is a known-key conversion, not a promise to translate any incoming schema. The incoming `schema_url` is metadata; it does not select or execute an arbitrary schema transformation.

The collector must understand new vocabulary before qyl-owned emitters adopt it. Compatibility checks cover older and current keys, canonical-key precedence, vendor pass-through and capture denials. See the [SemanticConventions source](https://github.com/ANcpLua/Qyl.Telemetry.SemanticConventions) and the [collector ingestion source](https://github.com/ANcpLua/qyl/tree/main/services/qyl.collector.ingestion).

## Exception details

The exact canonical attributes `exception.message` and `exception.stacktrace` are retained after value sanitization,
including span events and structured log-body maps. These key exemptions do not permit other message keys, case variants
or descendants, and do not bypass credential or privacy denials.

Sanitization preserves useful text, line breaks and stack frames while redacting labeled credentials in connection
strings and headers, bearer/API tokens, JWTs, known token prefixes, and URL user information, queries and fragments.
Input work is bounded at 131,072 UTF-16 code units per field. Sanitized values are capped at 32,768 UTF-8 bytes, with
truncation applied after redaction.

Invalid input or a sanitization failure replaces only the affected value with `[SANITIZATION_FAILED]`. Sibling
attributes and the record survive. Failure diagnostics contain a canonical key and fixed category, without the original
text or sanitizer exception message.

Unlabeled unknown secret formats, encoded/encrypted values, plain log bodies, span status descriptions and unrelated
attribute names are outside this exception-text policy. Existing stored data is unchanged. The
[persistence contract](https://github.com/ANcpLua/qyl/blob/main/docs/attribute-persistence.md) lists supported locations,
redaction forms and limits.

## Ingestion

The collector accepts official OTLP protobuf or JSON for traces, logs and metrics, and retains all three in DuckDB. Profiles are not supported.

In production, the OTLP receiver requires an `x-otlp-api-key` credential with the explicit `ingest` role. Configure each `QYL_OTLP_PROJECT_KEYS` entry as an object with `key` and a nonempty `roles` array; string-only keys and missing roles fail startup. Roles are independent: ingest access grants no product API permissions, and `read`, `write` or `delete` access grants no ingest permission. Local development defaults to unsecured loopback listeners.

## MCP operation telemetry

The qyl MCP server records its operation spans, duration histograms and operation logs using the generated qyl registry bindings for the MCP semantic vocabulary, and exports them to the caller's Collector project. A valid W3C `traceparent` in the request's `params._meta` becomes the parent of the server's `tools/call` span; `tracestate` and baggage are not read.

The server does not record prompt variables, tool arguments, tool results or arbitrary HTTP headers as span attributes. Collector failures reach the agent as errors; the server has no demonstration data to substitute.

## Captured headers

Capturing HTTP headers or RPC metadata is opt-in at the instrumentation that records them. The Collector keeps no second allowlist: after its explicit denials it retains every valid captured `http.request.header.*`, `http.response.header.*`, `rpc.request.metadata.*` and `rpc.response.metadata.*` field, including `authorization`, `cookie`, `x-api-key` and `mcp-param-*`. Choose what to capture at the source.
